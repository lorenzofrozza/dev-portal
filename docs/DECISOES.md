# Registro de decisões técnicas

Formato: data — decisão — alternativas consideradas — motivo. Este arquivo alimenta o artigo final (seção de desenvolvimento). Registrar aqui toda escolha não óbvia feita durante os ciclos.

- 2026-10-02 — **Tailwind v4 compilado no build** em vez de CSS puro com tokens — alternativas: CSS puro (zero dependências), Tailwind via CDN (descartado: viola a regra de runtime sem terceiros) — motivo: velocidade de desenvolvimento nos ciclos; a dependência é só de build (devDependency), o artefato final continua estático e auto-hospedado.
- 2026-10-02 — **Light DOM nos custom elements** — alternativa: Shadow DOM com CSS próprio por componente — motivo: classes utilitárias do Tailwind não atravessam shadow root; o encapsulamento visual não é requisito e o isolamento lógico se mantém por convenção (um arquivo por componente).
- 2026-10-02 — **Hash routing** — alternativa: History API — motivo: funciona no GitHub Pages e offline sem configuração de fallback de rotas no servidor.
- 2026-10-02 — **Fontes do sistema** (`system-ui`) — alternativa: fonte própria auto-hospedada — motivo: zero requisições extras e carga menor; revisar no ciclo 5 se a identidade visual pedir fonte própria.
- 2026-11-15 — **Aleatoriedade do gerador CPF/CNPJ via `crypto.getRandomValues`**, descartando bytes 250–255 — alternativa: `Math.random()` — motivo: API nativa (sem rede) com distribuição uniforme; o descarte evita que `byte % 10` favoreça os dígitos 0–5 (conferido: 5.000 CPFs, cada dígito entre 9,7% e 10,4%).
- 2026-11-15 — **CNPJ gerado sempre com filial 0001 (matriz)** — alternativa: filial aleatória — motivo: é o formato mais comum em cadastros de teste; os 8 dígitos da raiz continuam aleatórios.
- 2026-11-15 — **CPF com todos os dígitos iguais é descartado na geração e recusado na validação** — motivo: sequências como 111.111.111-11 passam no cálculo do DV, mas sistemas reais as rejeitam; gerá-las produziria dado de teste inútil.
- 2026-11-15 — **Histórico do gerador no escopo do módulo, não no componente nem no `localStorage`** — alternativa: guardar no elemento (perde ao trocar de ferramenta) ou em `localStorage` (persiste conteúdo gerado, contra a regra 5) — motivo: sobrevive à navegação entre ferramentas e some ao recarregar a página, que é a definição de "sessão" do RF09. Lista única com CPF e CNPJ marcados, máximo de 10.
- 2026-11-15 — **Validador sem `<form>`** (botão + Enter no campo) — motivo: um `<form>` pode virar submit e levar o conteúdo digitado na URL se o JavaScript falhar; sem ele, não existe caminho de rede para o dado, o que é mais fácil de defender na inspeção.
- 2026-11-15 — **Cópia com alternativa via `execCommand('copy')`** quando a Clipboard API é negada — motivo: navegadores embutidos e WebViews bloqueiam `navigator.clipboard`; a alternativa é local e mantém o RF09 funcionando nesses ambientes.
- 2026-11-15 — **CNPJ alfanumérico não suportado nesta versão**: o validador detecta letras e avisa — motivo: escopo fechado em 4 ferramentas; o novo formato da Receita fica no backlog (REQUISITOS.md), mas a entrada não é tratada como erro genérico.
- 2026-11-15 — **Busca do testador de regex num Web Worker com limite de 2 s** — alternativas: rodar na thread principal limitando o tamanho do texto, ou só avisar — motivo: regex com backtracking catastrófico (ex.: `(a+)+$`) trava a thread por minutos e não pode ser interrompida; no worker, a interface segue responsiva (medido: 10 de 10 ticks de 100 ms durante a busca) e o worker é encerrado ao estourar o limite (caso R5).
- 2026-11-15 — **Worker criado a partir de um Blob com o código do próprio componente** — alternativa: arquivo `regex-worker.js` separado — motivo: mantém "um arquivo por ferramenta" e não acrescenta asset ao `sw.js`; o Blob é montado em memória, sem rede. O worker nasce quando a ferramenta abre (antes de qualquer digitação) e só é recriado se uma busca for interrompida.
- 2026-11-15 — **Erro de sintaxe validado na thread principal, antes do worker** — motivo: `new RegExp` só compila (não tem risco de travar), então o RF15 responde na hora; a mensagem do navegador é traduzida para pt-BR por tabela (V8, SpiderMonkey e JavaScriptCore escrevem diferente) e mostrada também na forma original.
- 2026-11-15 — **Destaque montado com nós de texto, nunca `innerHTML`** — motivo: o texto de teste é conteúdo do usuário; HTML colado (ex.: `<img onerror>`) aparece como texto e não executa.
- 2026-11-15 — **Service Worker instala com `cache: 'reload'`** — motivo: o GitHub Pages envia `Cache-Control: max-age=600`; sem isso, logo após um deploy o SW novo podia gravar no cache offline cópias antigas guardadas pelo navegador, que ficariam até a próxima troca de `VERSION`.
- 2026-11-15 — **Diff por LCS com programação dinâmica, depois de separar prefixo e sufixo iguais** — alternativa: algoritmo de Myers (O(ND)) — motivo: LCS é o algoritmo pedido no RF18 e o mais fácil de explicar no artigo; separar as pontas iguais deixa a tabela pequena nos casos reais (mudança pontual em arquivo de 500 linhas: < 0,1 ms). Linhas viram inteiros antes da tabela, que usa `Uint16Array`.
- 2026-11-15 — **Limite de 10 milhões de células na tabela da LCS (~20 MB)** — motivo: o pior caso dentro do limite (3.000 × 3.000 linhas todas diferentes) leva ~15 ms; acima disso o portal recusa com aviso em vez de travar ou estourar a memória do celular.
- 2026-11-15 — **Diff unificado no formato `diff -u` padrão (contexto de 3 linhas)** — motivo: o resultado copiado pode ser aplicado com `patch`/`git apply`. Verificado: 200 diffs aleatórios aplicados com o `patch` do sistema reproduziram o texto modificado byte a byte.
- 2026-11-15 — **Quebras `\r\n`, `\r` e `\n` tratadas como iguais; quebra final não conta como linha** — motivo: texto colado do Windows não pode aparecer como "tudo mudou"; quando os textos diferem só nisso, a ferramenta avisa ("sem diferenças nas linhas").
- 2026-11-15 — **Visualização lado a lado só a partir de 768 px** — motivo: em 360 px duas colunas de código ficam ilegíveis; no celular a visualização é sempre unificada (com sinais + e −, não só cor, para quem não distingue vermelho e verde).
- 2026-11-15 — **Linhas iguais longe das mudanças aparecem recolhidas** ("⋯ N linhas iguais") — motivo: numa mudança no meio de 500 linhas, mostrar tudo esconderia a mudança; o critério é o mesmo dos blocos do diff unificado.
- 2026-11-15 — **RF02: localização do erro de JSON feita pelo próprio portal** — alternativa: ler a posição da mensagem do `JSON.parse` — motivo: cada navegador escreve a mensagem de um jeito e o Chrome atual omite a posição em vários erros, então o RF02 falhava. O `JSON.parse` nativo continua decidindo se o JSON é válido; só quando ele recusa, um analisador de ~150 linhas percorre a gramática do JSON (RFC 8259) e aponta linha, coluna e motivo em pt-BR (vírgula sobrando, aspas simples, campo sem aspas, `True`/`undefined`, zero à esquerda, comentário, espaço invisível…). Conferido: concorda com o `JSON.parse` em 20.000 entradas mutadas aleatoriamente.
- 2026-11-15 — **Analisador iterativo, com pilha explícita** — motivo: uma versão recursiva estoura a pilha com JSON muito aninhado; testado com 100.000 níveis.
- 2026-11-15 — **Coluna conta caracteres, não unidades UTF-16** — motivo: um emoji ocupa duas unidades em JavaScript; sem esse cuidado, a coluna apontada fica errada em textos com emoji.
- 2026-11-15 — **Vírgula sobrando é apontada na vírgula, não no `}` seguinte** — motivo: é ali que o usuário precisa apagar; os navegadores apontam o caractere seguinte, que pode estar linhas abaixo.
- 2026-11-15 — **Formatar/minificar reescreve só os espaços, sem passar por `JSON.stringify`** — motivo: `JSON.stringify(JSON.parse(x))` altera dados silenciosamente — arredonda inteiros acima de 2^53 (IDs de 19 dígitos viram outro número), troca `1.0` por `1`, reordena chaves numéricas e descarta campos repetidos. O formatador copia textos e números exatamente como vieram; para JSON comum o resultado é idêntico ao do `JSON.stringify` (conferido em 2.000 JSONs aleatórios).
- 2026-11-15 — **Trecho do erro na área de saída** (linha anterior, linha do erro, `^` na coluna) e botão "Mostrar na entrada", que seleciona o caractere no campo — motivo: a tarefa 1 do SUS pede para corrigir um JSON inválido; o foco só muda quando o usuário pede (mover o foco sozinho atrapalha leitores de tela).
- 2026-11-15 — **Testes automatizados com `node:test`, sem dependências** — alternativa: Jest/Vitest — motivo: a regra de dependências mínimas vale também para testes; o executor embutido no Node basta. Os componentes rodam no Node com três stubs (`HTMLElement`, `customElements`, `matchMedia`), sem simular o DOM. A interface é testada no navegador.
- 2026-11-15 — **Cores do diff reforçadas após uso real** — motivo: o fundo vermelho/verde claro (os mesmos tons dos avisos) ficava fraco com código real, e as duas metades do lado a lado se misturavam. Agora cada linha alterada tem fundo mais saturado, faixa mais forte na numeração e barra colorida na borda esquerda; onde a linha não existe de um lado, aparecem listras em vez de branco; uma divisória separa as metades. Tokens próprios (`red-line`, `red-gutter`, `leaf-line`, `leaf-gutter`) com contraste AA conferido: texto ≥ 10:1, sinais − e + ≥ 4,5:1.
